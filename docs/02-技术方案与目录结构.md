# 02 技术方案与目录结构

> 版本：V1（第一版，可试用版）
> 状态：规划稿，等待负责人确认后开工
> 前置文档：[01 产品定位与需求](./01-产品定位与需求.md)

## 1. 设计原则

1. **接口先行，单一来源**：前后端共用的类型、校验规则和接口定义只存放在 `packages/shared` 中，并且只由主 Agent 修改。前端（A）、后端（B）和验收（C）都依据它并行开发。
2. **外部依赖全部可替换**：数据来源、大模型、邮件发送都定义为接口（adapter）。第一版各提供一个“离线实现”（CSV、模板、模拟发送），**不需要任何账号和网络也能完整演示**。
3. **个人信息不出本地**：大模型只接收人群统计特征；个性化（姓名、商品名、折扣码）在本地通过占位符渲染。
4. **合规写在服务端**：退订链接检查、营销同意过滤、删除逻辑都在后端强制执行，不依赖前端判断。
5. **快照可追溯**：活动创建时冻结收件人名单；每次调用大模型都记录供应商、模型、模板版本和耗时，但不记录 Key。
6. **简单优先**：单进程后端，SQLite 单文件数据库，发送任务使用进程内队列；等试用规模扩大后再拆分。

## 3. 总体架构

```
┌──────────────────────── apps/web（React，中文界面）────────────────────────┐
│ 首页(节点提醒) │ 数据导入 │ 客户 │ 分群 │ 活动(创建/文案/审核/发送) │ 报表 │ 设置 │
└───────────────────────────────┬────────────────────────────────────────────┘
                                │ HTTP JSON /api/v1（类型来自 packages/shared）
┌───────────────────────────────┴──── apps/api（Fastify）─────────────────────┐
│ auth  stores  imports  customers  segments  calendar  campaigns              │
│ content  sending  tracking  privacy                                          │
│                                                                              │
│ adapters/                                                                    │
│   datasource/  shopify-csv（第一版） │ shopify-api（预留接口，未实现）         │
│   llm/         openai │ deepseek │ doubao │ template（离线兜底）              │
│   email/       mock（默认） │ smtp                                           │
└───────────────┬─────────────────────────────┬────────────────────────────────┘
                │                             │
           SQLite 文件                  外部服务（全部可选）
                                    GPT / DeepSeek / 豆包 / SMTP
```

### 3.1 主流程

1. **导入**：上传 CSV，由 `DataSource` 适配器解析为标准结构，逐行校验并返回预览；用户确认后在一个事务中写入数据库（按外部 ID upsert）；然后重算客户画像，并计算已发送活动的转化。
2. **分群**：根据场景规则和分层条件，从 `customer_profiles` 中查询，实时返回人数、可触达人数、语言分布和国家分布。
3. **活动**：创建活动时冻结收件人名单（`campaign_recipients`），并记录每个人被排除的原因，例如未同意营销、已退订、缺少邮箱或手机号、在对照组中、触发频率限制。
4. **生成**：对收件人中出现的每种语言，调用文案生成链路，得到 N 个版本；再调用中文对照和检查链路；结果保存为草稿。
5. **审核**：运营编辑文案、通过或驳回；后端重新运行规则检查。
6. **发送或导出**：邮件按收件人逐个渲染占位符（含专属退订链接），交给 `EmailSender`；WhatsApp 按收件人渲染后导出 CSV。
7. **追踪**：模拟发送会产生确定性的模拟事件；真实发送通过点击跳转链接、可选的打开像素和退订页面记录事件；导入新订单后按归因规则计算转化。

## 4. 适配器接口

接口定义在 `apps/api/src/adapters/*/types.ts` 中，属于后端内部实现，不放进 shared。

### 4.1 数据来源

```ts
interface DataSource {
  kind: 'shopify_csv' | 'shopify_api';
  parseCustomers(input: Readable): AsyncIterable<RowResult<NormalizedCustomer>>;
  parseOrders(input: Readable): AsyncIterable<RowResult<NormalizedOrder>>;
  parseAbandonedCheckouts(input: Readable): AsyncIterable<RowResult<NormalizedCheckout>>;
  parseProducts(input: Readable): AsyncIterable<RowResult<NormalizedProduct>>;
}
```

Shopify CSV 的要点（需要用真实导出文件核对）：

- 客户 CSV：`Customer ID`、`First Name`、`Last Name`、`Email`、`Accepts Email Marketing`、`Accepts SMS Marketing`、`Phone`、`Default Address Country Code`、`Tags`、`Total Spent`、`Total Orders`。
- 订单 CSV：**每个商品占一行**，订单级字段只在该订单的第一行填写，需要按 `Name` 合并。订单中**没有客户 ID**，需要用 `Email` 关联到客户。关键字段包括 `Name`、`Id`、`Email`、`Financial Status`、`Created at`、`Currency`、`Total`、`Discount Code`、`Lineitem name`、`Lineitem sku`、`Lineitem quantity`、`Lineitem price`、`Shipping Country`、`Accepts Marketing`。
- 退款或取消的订单（`Financial Status` 为 refunded 或 voided）不计入消费和转化。
- 列名匹配时忽略大小写和首尾空格；无法识别的列在预览中列出，但不报错。

以后接入 Shopify API 时，只需要新增 `shopify-api` 适配器输出相同的标准结构，导入之后的流程不变。

### 4.2 大模型

```ts
interface LlmProvider {
  id: 'openai' | 'deepseek' | 'doubao' | 'template';
  isConfigured(): boolean;               // 检查对应的环境变量是否齐全
  completeJson<T>(req: LlmJsonRequest<T>): Promise<LlmResult<T>>;
}
```

- `openai`、`deepseek`、`doubao` 共用一个 OpenAI 兼容的客户端，只是 base URL、Key 和模型名不同。
- `template`：根据“场景 × 语言 × 渠道”从内置模板库中选择文案并填入活动信息，中文对照同样来自模板。它始终可用，不访问网络。
- **路由链**：每种用途按顺序尝试供应商，跳过未配置的供应商；某个供应商失败（超时、5xx 错误、输出不符合 schema 且重试 1 次仍失败）后，自动尝试下一个。

| 用途 | 默认链（可以通过环境变量覆盖） |
| --- | --- |
| `copywrite`（外语文案） | `openai → deepseek → template` |
| `translate_zh`（中文对照） | `deepseek → openai → template` |
| `review`（AI 检查） | `deepseek → openai → 跳过（只保留规则检查）` |

- 豆包通过在链中加入 `doubao` 来启用，例如 `LLM_CHAIN_COPYWRITE=doubao,deepseek,template`。
- 每次调用都写入 `llm_calls`：用途、供应商、模型、是否为降级结果、耗时、token 数和错误摘要；不保存 Key 和请求头。
- 前端在每个文案版本上显示“由 GPT / DeepSeek / 豆包 / 模板生成”，降级时给出提示。

### 4.3 邮件发送

```ts
interface EmailSender {
  id: 'mock' | 'smtp';
  send(msg: OutgoingEmail): Promise<SendResult>;   // OutgoingEmail 含 List-Unsubscribe 头
}
```

- `mock`（默认）：不访问网络，把邮件写入 `messages` 表，状态设为 `delivered`，并根据收件人 ID 的哈希生成确定性的模拟打开、点击和转化数据，保证演示和测试结果可以复现。界面上明确标注“模拟发送”。
- `smtp`：配置 `EMAIL_SENDER=smtp` 和 SMTP 相关环境变量后启用。
- 发送在进程内队列中执行，限速可配置；单封邮件失败不影响其他邮件，失败原因会被记录。

## 5. 数据结构草图（SQLite）

所有业务表都包含 `id`（字符串 UUID）、`store_id`、`created_at` 和 `updated_at`。所有查询都必须带上 `store_id` 条件。

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `users` | email, password_hash, store_id | 由管理员脚本创建 |
| `stores` | name, brand_voice, sender_name, reply_to, company_address, currency, timezone, country_language_map(JSON), repurchase_cycles(JSON) | 店铺设置 |
| `import_batches` | kind, filename, status, total_rows, valid_rows, error_rows, inserted, updated, errors(JSON) | 导入批次 |
| `customers` | external_id, email, phone_e164, first_name, last_name, country, language, tags(JSON), email_consent, sms_consent, unsubscribed_at | 唯一键为 (store_id, external_id) |
| `orders` | external_id, name, customer_id, email, created_at_shop, total, currency, discount_code, financial_status, country | 唯一键为 (store_id, external_id) |
| `order_items` | order_id, sku, title, category, quantity, price | |
| `products` | sku, title, category | 来自商品 CSV，用于映射品类 |
| `checkouts` | external_id, email, customer_id, created_at_shop, total, items(JSON), recovered | 弃单 |
| `customer_profiles` | customer_id, order_count, total_spent, aov, first_order_at, last_order_at, spend_tier, top_categories(JSON), last_purchase_by_category(JSON) | 导入后重算 |
| `campaigns` | name, scenario, filters(JSON), channels(JSON), intent_zh, offer(JSON), holiday_key, holdout_pct, status | |
| `campaign_recipients` | campaign_id, customer_id, language, channel, included, exclusion_reason, is_holdout | 冻结的收件人名单 |
| `content_variants` | campaign_id, channel, language, index, subject, preview_text, body, translation_zh(JSON), status, edited, provider, model, is_fallback, check_issues(JSON) | |
| `llm_calls` | purpose, provider, model, is_fallback, latency_ms, tokens_in, tokens_out, ok, error | |
| `messages` | campaign_id, recipient_id, variant_id, channel, sender, status, unsubscribe_token, sent_at, error | |
| `message_events` | message_id, type(delivered/opened/clicked/unsubscribed/bounced), occurred_at, simulated | |
| `conversions` | campaign_id, customer_id, order_id, revenue, via_discount_code, is_holdout | 导入订单后计算 |
| `audit_logs` | user_id, action, target_type, target_id, detail(JSON) | 删除操作只记录数量，不记录个人信息 |

删除规则：删除单个客户时，物理删除 `customers`、`customer_profiles`、`campaign_recipients`、`messages` 中该客户的数据；`orders`、`checkouts` 中该客户的记录同样删除；`conversions` 只保留汇总所需的金额，并去掉客户关联；`audit_logs` 只记录“删除 1 位客户”。

### 6.4 主要错误码

`UNAUTHORIZED`、`FORBIDDEN`、`NOT_FOUND`、`VALIDATION_FAILED`、`IMPORT_EMPTY`、`IMPORT_UNRECOGNIZED`、`IMPORT_ALREADY_COMMITTED`、`VARIANT_HAS_BLOCKING_ISSUES`、`CAMPAIGN_NOT_READY`（还有语言没有通过审核的版本）、`MISSING_UNSUBSCRIBE`、`MISSING_COMPANY_ADDRESS`、`NO_ELIGIBLE_RECIPIENTS`、`LLM_ALL_PROVIDERS_FAILED`、`CONFIRMATION_MISMATCH`。

### 6.5 接口变更流程

只有主 Agent 可以修改 `packages/shared`。子 Agent 发现接口不够用时，在自己 PR 的描述中写明“接口变更请求”。主 Agent 评估后，单独提交一个 shared PR，同时更新本节和 `packages/shared/CHANGELOG.md`，合并后通知各子 Agent rebase。具体规则见 [04 Agent 分工与协作](./04-Agent分工与协作.md)。

## 7. 文案检查规则

规则检查由后端执行，是阻止审核通过和发送的依据：

| 规则 | 级别 |
| --- | --- |
| 邮件正文缺少 `{{unsubscribe_url}}` | 严重（阻止） |
| 邮件页脚缺少 `{{company_address}}` | 严重（阻止） |
| 出现白名单以外的占位符，或占位符没有闭合 | 严重（阻止） |
| 文案语言与目标语言不一致（基于简单的语言检测） | 严重（阻止） |
| 邮件标题超过 80 个字符；WhatsApp 消息超过 1000 个字符 | 警告 |
| 命中夸大或违禁词表（英语和西班牙语，例如 “guaranteed”、“100% cure”、“garantizado”） | 警告 |

AI 检查（DeepSeek）只输出警告：语气是否符合品牌、是否有误译或文化冒犯风险、中文对照是否与原文一致。AI 检查失败时，不影响规则检查的结果。

| `PUBLIC_BASE_URL` | 退订和追踪链接使用的公网地址 |

| `LLM_TIMEOUT_MS` | 单次调用超时时间 |
| `EMAIL_SENDER` | `mock`（默认）或 `smtp` |
| `SMTP_HOST` / `SMTP_PORT` / `SMTP_USER` / `SMTP_PASS` / `SMTP_FROM` | 真实发送 |
| `SEND_RATE_PER_MIN` | 发送限速 |

没有配置任何 Key 时：文案和中文对照都由模板生成，AI 检查跳过，邮件为模拟发送。整套演示流程可以在完全离线的环境中完成。

## 10. 主要风险与对策

| 风险 | 对策 |
| --- | --- |
| 真实的 Shopify 导出格式与预期不同（列名变化、多语言后台） | 列名匹配时忽略大小写和空格，并支持别名；预览中列出未识别的列；试用前用真实文件核对 |
| 订单 CSV 中没有客户 ID | 用邮箱关联；关联不上的订单在预览中单独计数 |
| 大模型输出不稳定或超时 | 用 JSON schema 校验，失败重试 1 次，然后按路由链降级，最后由模板兜底 |
| 模拟数据被误认为真实效果 | 模拟事件带 `simulated` 标记，报表中明确标注 |
| 真实发送进垃圾箱 | 第一版只负责合规内容（退订链接、List-Unsubscribe 头、公司地址）和限速；送达率由卖家的邮件服务商负责 |
| 三个子 Agent 并行时冲突 | 严格按目录划分归属；shared 只由主 Agent 修改；lockfile 规则见 04 |
| 泄露密钥 | 只从环境变量读取；验收中检查仓库里没有密钥特征串；日志会脱敏 |
