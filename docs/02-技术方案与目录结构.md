# 02 技术方案与目录结构

> 版本：V0.1（第一阶段）
> 状态：规划稿，等待负责人确认
> 前置文档：[01 产品定位与需求](./01-产品定位与需求.md)

## 1. 设计原则

1. **接口先行**：先定好前后端接口和模块边界，三个 Agent 才能并行开发而互不阻塞。本文第 6 节就是这份接口约定。
2. **AI 能力可替换、可离线**：所有大模型调用都经过统一的供应商抽象层。测试和本地开发默认使用 Mock 供应商，**不需要真实的 API Key 也能完整跑通**。
3. **规则数据化**：分群口径、阈值、提示词模板都放在数据或配置中，并带有版本号，不在业务代码里写死。
4. **快照而非实时**：营销活动引用分群时，保存当时的成员快照。这样即使之后重新导入数据，已生成的内容和导出的名单仍然可以解释。
5. **简单优先**：第一阶段不引入消息队列和微服务；AI 生成先同步调用，并设置超时。

## 2. 技术选型（建议，待确认）

沿用团队上一个项目已经验证过的技术栈，降低学习和运维成本。

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 后端 | Python 3.12 + FastAPI | 方便做数据处理（pandas），调用大模型的生态成熟 |
| ORM 与迁移 | SQLAlchemy 2.x + Alembic | 所有表结构变更都必须通过迁移脚本完成 |
| 数据库 | PostgreSQL 16 | 分群条件、生成参数等使用 JSONB 存储 |
| 数据处理 | pandas | 解析和校验 CSV |
| 大模型 | 兼容 OpenAI 的 HTTP 接口（`httpx` 直接调用） | 通过配置切换 DeepSeek、通义千问、OpenAI 等；内置 Mock 供应商 |
| 前端 | React + TypeScript + Vite | 组件库建议用 Ant Design（中文后台场景成熟） |
| 测试 | 后端 pytest；前端 Vitest + Testing Library | Mock 大模型，测试中不访问外网 |
| 部署 | Docker Compose（db + backend + frontend） | 一条命令启动演示环境 |

## 3. 总体架构与数据流

```
          ┌───────────────────────── 前端 (React) ─────────────────────────┐
          │ 店铺设置 │ 数据导入 │ 客户分群 │ 营销活动 │ 内容审核 │ 导出记录 │
          └──────────────────────────────┬─────────────────────────────────┘
                                         │ REST JSON（/api/v1）
┌────────────────────────────────────────┴────────────────────────────────────────┐
│                                后端 (FastAPI)                                   │
│                                                                                 │
│  imports ──► customers(画像汇总) ──► segments(分群计算/快照) ──┐                  │
│   CSV 预览/校验/入库    RFM、复购间隔等指标      预置+自定义规则  │                 │
│                                                              ▼                  │
│                                  campaigns ──► ai(生成服务) ──► compliance(检查) │
│                                  活动/草稿/审核   提示词模板+供应商抽象              │
│                                       │                                         │
│                                       ▼                                         │
│                                  exports（名单 CSV / 内容 HTML，写导出记录）       │
└────────────────────────────────────────┬────────────────────────────────────────┘
                                         │
                                  PostgreSQL         大模型 API（或 Mock）
```

主流程：

1. **导入**：上传 CSV，后端解析并逐行校验，返回预览（合法行数、错误行和原因）；用户确认后在同一个事务中入库，并生成导入批次记录。
2. **画像汇总**：导入成功后，按店铺重新计算客户指标，写入 `customer_metrics`。
3. **分群**：根据规则计算成员；列表页展示实时人数；创建营销活动时生成 `segment_snapshot`。
4. **生成**：根据快照计算聚合特征（不含个人信息），结合活动参数渲染提示词模板，调用大模型，解析出结构化结果，再运行合规检查，保存为草稿。
5. **审核**：用户编辑内容，并把状态改为通过或驳回。
6. **导出**：只允许导出已通过的内容；名单默认过滤掉未同意营销的客户；写入导出记录。

## 4. 数据结构草图

所有业务表都带 `id`（UUID）、`created_at` 和 `updated_at`。业务数据按 `store_id` 隔离。

### 4.1 店铺与原始数据

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `stores` | name, platform, currency, timezone, brand_name, brand_voice, main_categories | 店铺和品牌上下文 |
| `import_batches` | store_id, kind(customers/orders), filename, status(previewed/committed/failed), total_rows, valid_rows, error_rows, errors(JSONB) | 导入批次 |
| `customers` | store_id, external_id, email, first_name, last_name, country, accepts_marketing, tags, source_batch_id | 唯一键为 (store_id, external_id)；没有外部 ID 时用 email |
| `orders` | store_id, external_id, customer_id, ordered_at, total_amount, currency, discount_code, financial_status | 唯一键为 (store_id, external_id) |
| `order_items` | order_id, sku, product_title, product_type, quantity, unit_price | `product_type` 用作品类 |

### 4.2 画像与分群

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `customer_metrics` | customer_id, order_count, total_spent, avg_order_value, first_order_at, last_order_at, days_since_last_order, avg_repurchase_days, discount_order_ratio, r_score, f_score, m_score, categories(JSONB), computed_at | 由导入后的重算生成，可以整体重建 |
| `segments` | store_id, name, kind(preset/custom), preset_key, rule(JSONB), rule_version, is_active | 分群定义 |
| `segment_snapshots` | segment_id, rule(JSONB), member_count, features(JSONB), created_at | 冻结的分群；`features` 保存聚合特征 |
| `segment_snapshot_members` | snapshot_id, customer_id | 快照成员 |

分群规则 `rule` 的格式（第一阶段只支持“且”）：

```json
{
  "all": [
    {"field": "order_count", "op": "eq", "value": 1},
    {"field": "days_since_first_order", "op": "between", "value": [30, 60]}
  ]
}
```

允许的字段和比较符由后端白名单 `segments/fields.py` 定义，并通过 `GET /segments/fields` 提供给前端，用于渲染条件编辑器。

### 4.3 营销活动与 AI 内容

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `campaigns` | store_id, name, snapshot_id, channel(email), goal_zh, target_language, tone, offer(JSONB), variant_count, status(draft/ready/exported) | 营销活动 |
| `prompt_templates` | key, version, channel, system_prompt, user_prompt, output_schema(JSONB), is_active | 提示词模板，带版本，由迁移或种子脚本写入 |
| `content_variants` | campaign_id, index, subject, preview_text, body_html, body_text, translation_zh(JSONB), status(draft/approved/rejected), edited, compliance_issues(JSONB) | 内容版本 |
| `generation_runs` | campaign_id, variant_id, provider, model, template_key, template_version, input_features(JSONB), raw_output, prompt_tokens, completion_tokens, latency_ms, status, error | 每次调用大模型的记录，用于追溯和排查问题 |

### 4.4 导出与日志

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `export_records` | campaign_id, kind(audience_csv/content_html/content_text), row_count, include_non_consented, created_by | 导出记录 |
| `users` | email, password_hash | 简单登录（P1） |
| `operation_logs` | user_id, action, target_type, target_id, detail(JSONB) | 关键操作日志 |

## 5. AI 生成设计

### 5.1 供应商抽象

```python
class LLMProvider(Protocol):
    name: str
    def complete_json(self, *, system: str, user: str, schema: dict,
                      model: str, timeout_s: float) -> LLMResult: ...
```

- `OpenAICompatibleProvider`：通过 `LLM_BASE_URL`、`LLM_API_KEY` 和 `LLM_MODEL` 配置，覆盖 DeepSeek、通义千问（兼容模式）和 OpenAI。
- `MockProvider`：根据输入确定性地返回符合 schema 的内容，用于测试、演示和前端联调。`LLM_PROVIDER=mock` 是默认值。

### 5.2 输入（不含个人信息）

```json
{
  "store": {"brand_name": "...", "brand_voice": "...", "main_categories": ["..."]},
  "segment": {"name": "新客首单未复购", "member_count": 312,
              "avg_order_value": 46.2, "top_categories": ["..."],
              "top_countries": ["US", "GB"], "discount_order_ratio": 0.31},
  "campaign": {"goal_zh": "...", "tone": "friendly", "target_language": "en",
               "offer": {"type": "percent", "value": 10, "code": "WELCOME10"}}
}
```

### 5.3 输出（结构化 JSON，由 schema 校验）

```json
{
  "variants": [
    {"subject": "...", "preview_text": "...", "body_html": "...",
     "body_text": "...", "translation_zh": {"subject": "...", "body": "..."}}
  ]
}
```

- 正文中只允许使用约定的占位符：`{{first_name}}`、`{{discount_code}}`、`{{unsubscribe_link}}`、`{{shop_url}}`。
- 解析失败时自动重试 1 次；仍然失败时，`generation_runs.status=failed`，并向前端返回可读的错误信息。

### 5.4 合规检查（`ai/compliance.py`）

基于规则，不调用大模型：

- 缺少 `{{unsubscribe_link}}`：严重级别为 error。
- 出现白名单以外的 `{{...}}` 占位符：error。
- 命中夸大或违禁词表，例如 “guaranteed”、“100% cure”、“best in the world”：warning。
- 标题长度超过 80 个字符：warning。

检查结果写入 `content_variants.compliance_issues`。存在 error 级别问题时，不允许将内容标记为“已通过”。

## 6. 接口约定（前后端契约）

统一前缀 `/api/v1`，请求和响应都使用 JSON（上传接口除外）。错误响应格式统一为 `{"error": {"code": "...", "message": "...", "details": ...}}`。列表接口支持 `?page=&page_size=`，返回 `{"items": [...], "total": n}`。

| 方法 | 路径 | 说明 | 负责人 |
| --- | --- | --- | --- |
| GET | `/health` | 健康检查 | A |
| POST | `/auth/login` | 登录，返回 token（P1） | A |
| GET/POST | `/stores` | 店铺列表 / 创建 | A |
| GET/PATCH | `/stores/{store_id}` | 店铺详情 / 更新品牌信息 | A |
| POST | `/stores/{store_id}/imports/preview` | 上传 CSV（multipart，`kind=customers\|orders`），返回预览 | A |
| POST | `/stores/{store_id}/imports/{batch_id}/commit` | 确认入库，并触发画像重算 | A |
| GET | `/stores/{store_id}/imports` | 导入批次列表 | A |
| GET | `/stores/{store_id}/customers` | 客户列表（含指标，支持按分群过滤） | A |
| GET | `/segments/fields` | 自定义分群可用的字段和比较符 | A |
| GET/POST | `/stores/{store_id}/segments` | 分群列表（含实时人数） / 创建自定义分群 | A |
| POST | `/stores/{store_id}/segments/preview` | 按规则预览人数和特征（不保存） | A |
| GET | `/segments/{segment_id}` | 分群详情：规则、人数、聚合特征 | A |
| GET/POST | `/stores/{store_id}/campaigns` | 活动列表 / 创建活动（同时生成分群快照） | B |
| GET | `/campaigns/{campaign_id}` | 活动详情（含快照特征和全部内容版本） | B |
| POST | `/campaigns/{campaign_id}/generate` | 生成全部内容版本 | B |
| POST | `/campaigns/{campaign_id}/variants/{variant_id}/regenerate` | 重新生成单个版本 | B |
| PATCH | `/campaigns/{campaign_id}/variants/{variant_id}` | 编辑内容（编辑后重新执行合规检查） | B |
| POST | `/campaigns/{campaign_id}/variants/{variant_id}/review` | `{"decision": "approve\|reject"}` | B |
| POST | `/campaigns/{campaign_id}/exports` | `{"kind": "...", "include_non_consented": false}`，返回文件下载 | B |
| GET | `/campaigns/{campaign_id}/exports` | 导出记录 | B |

B 在创建快照和计算聚合特征时，通过 A 提供的 Python 服务函数调用（见第 8 节），不经过 HTTP。

正式的请求和响应字段以 FastAPI 生成的 OpenAPI 文档为准。前端类型由 C 依据 OpenAPI 维护在 `frontend/src/api/types.ts` 中。接口字段变更必须同时更新本节和 `docs/api-changelog.md`（第一次变更时创建）。

## 8. 模块间的 Python 接口（A 提供给 B）

为了让 B 不依赖 A 的内部实现，A 在 `app/segments/service.py` 中稳定提供以下函数（签名变更必须通知 B）：

```python
def create_snapshot(db: Session, segment_id: UUID) -> SegmentSnapshot: ...
def get_snapshot_features(db: Session, snapshot_id: UUID) -> SegmentFeatures: ...
def iter_snapshot_members(db: Session, snapshot_id: UUID,
                          consented_only: bool = True) -> Iterator[CustomerExportRow]: ...
```

`SegmentFeatures` 和 `CustomerExportRow` 是定义在 `app/segments/schemas.py` 中的 Pydantic 模型。在 A 完成实现之前，B 可以先用同签名的桩函数开发。

## 10. 主要风险与对策

| 风险 | 对策 |
| --- | --- |
| 各平台导出的 CSV 格式不一致 | 以 Shopify 格式作为标准；`imports/mapping.py` 支持列名映射；预览阶段明确列出无法识别的列 |
| 大模型输出格式不稳定 | 使用 JSON schema 校验，失败重试 1 次，保存原始输出以便排查 |
| 大模型成本和延迟 | 每次只生成 3 个版本，记录 token 用量；超时后返回可读错误 |
| 个人信息泄露给第三方模型 | 生成服务只接收 `SegmentFeatures`，类型上就无法传入客户明细；为此编写专门的测试 |
| 重新导入后历史内容无法解释 | 营销活动绑定分群快照，快照保存规则和成员 |
| 并行开发时接口不一致 | 遵守第 6 节和第 8 节的契约；C 先用 mocks 开发；联调前由 A 和 B 提供 OpenAPI 文档 |
