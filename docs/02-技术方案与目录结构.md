# 02 技术方案与目录结构

> 版本：V1（第一版，可试用版）
> 状态：**已确认**（2026-10-11），作为第一版的实现依据
> 前置文档：[01 产品定位与需求](./01-产品定位与需求.md)

## 1. 设计原则

1. **接口先行，单一来源**：前后端共用的类型、校验规则和接口定义只存放在 `packages/shared` 中，并且只由主 Agent 修改。前端（A）、后端（B）和验收（C）都依据它并行开发。
2. **以“每个客户一份文案”为核心建模**：数据结构的中心是“某次推广中某个客户的那份文案”，而不是“一个活动的一份文案”。
3. **外部依赖全部可替换**：数据来源、大模型、邮件发送都定义为接口（adapter），并各提供一个离线实现（CSV、模板、模拟发送），**不需要任何账号和网络也能完整演示**。
4. **省调用**：每个客户最多调用 1 次模型（外语和中文对照一起返回）；信息少的客户合并成小群生成；默认不做 AI 检查。
5. **个人信息不出本地**：发给模型的是“客户简报”，其中不含姓名、邮箱、手机号；备注中的隐私信息会被遮盖；个人信息在本地通过占位符填回。
6. **合规写在服务端**：退订链接、营销同意过滤、删除逻辑都在后端强制执行，不依赖前端判断。
7. **简单优先**：单进程后端，SQLite 单文件数据库，生成和发送任务使用进程内队列，限制并发数。后端启动时，把上次未完成的任务标记为“已中断，可重试”。
8. **统一入口**：所有发送、复制、渲染、导出都通过同一个“取可触达收件人”函数（`sending/eligibility.ts`）过滤同意状态、退订和删除，不允许各自编写查询。
9. **金额与时间**：金额以“分”为单位，用整数存储（字段名以 `_cents` 结尾）；时间统一存 UTC，“距今天数”按店铺时区计算。

### 3.1 主流程

1. **导入**：上传 CSV，由 `DataSource` 适配器解析为标准结构，逐行校验并返回预览；确认后在一个事务中 upsert；然后重算客户画像，并计算已发送推广的转化。
2. **完善画像**：销售为客户添加备注、偏好标签、客户类型，或修正语言。保存备注时检测其中的隐私信息并给出提示。
3. **挑选客户**：场景筛选、条件筛选和手动勾选组合成一份名单（≤ 单批上限），预览人数、可触达人数、语言分布。
4. **创建推广**：保存推广意图、渠道、优惠信息、关联的营销节点，并冻结收件人名单（`outreach_recipients`）。每个收件人记录：是否可触达及排除原因、生成方式（逐个定制或小群方式）、所属小群。
5. **预估**：根据逐个定制的人数和小群数，计算调用次数、预估 token 数和费用。
6. **生成（后台任务）**：
   - 逐个定制：为每个收件人构建“客户简报”，调用一次模型，同时返回外语文案和中文对照。
   - 小群方式：为每个小群构建“小群简报”，调用一次模型，然后把结果复制给小群中的每个收件人。
   - 每份结果都经过规则检查，保存为该收件人的草稿（`drafts`）。
   - 并发数可配置；单个失败只记录错误，不影响整个任务；可以只重试失败的部分。
7. **审核**：按优先级排序展示；可以编辑、通过、驳回；支持一键通过所有没有阻止性问题的草稿；可以对单份草稿点“帮我检查”（AI 检查）或“用高质量模型重写”。
8. **发送**：
   - 邮件：对已通过且可触达的收件人逐封渲染（填入个人信息和专属退订链接），交给 `EmailSender`。
   - 复制：接口返回某份草稿渲染后的最终文本，由前端复制。
   - WhatsApp：返回渲染后的文本和 wa.me 链接，或者批量导出 CSV。
9. **追踪**：模拟发送会产生确定性的模拟事件；真实发送通过点击跳转链接、可选的打开像素和退订页面记录事件；导入新订单后按归因规则计算转化。

## 4. 生成设计

### 4.1 客户简报（发给模型的内容，不含个人信息）

```json
{
  "store":    { "brand": "Paws Demo", "voice": "warm, playful", "currency": "USD" },
  "outreach": { "intent_zh": "黑五老客专享 8 折，主推猫砂和猫粮，强调囤货划算",
                "scenario": "segmented_promo", "holiday": "black_friday",
                "offer": { "type": "percent", "value": 20, "code": "{{discount_code}}" },
                "channels": ["email", "whatsapp"] },
  "customer": { "language": "es", "country": "MX", "customer_type": "retail",
                "order_count": 5, "spend_tier": "high", "days_since_last_order": 26,
                "purchases": [ { "title": "Dust-free Cat Litter 10L", "category": "cat_litter",
                                 "days_ago": 26, "quantity": 2 } ],
                "preference_tags": ["布偶猫", "无尘猫砂"],
                "notes": ["养了两只布偶猫，喜欢无尘猫砂", "上次反馈物流慢，已补偿"] }
}
```

- 简报由 `generation/brief.ts` 构建，**类型上不包含姓名、邮箱、手机号、地址字段**。
- 备注经过 `privacy/redact.ts` 处理：邮箱、电话、网址、门牌地址格式的内容会被替换成 `[已隐藏]`；只发送最近 5 条备注，每条最多 300 字。
- 购买记录只发送最近 10 条商品记录。

### 4.2 模型输出（JSON，由 schema 校验）

```json
{
  "email":    { "subject": "...", "preview_text": "...", "body": "..." },
  "whatsapp": { "text": "..." },
  "zh":       { "email": { "subject": "...", "preview_text": "...", "body": "..." },
                "whatsapp": { "text": "..." } },
  "personalization_points": ["提到无尘猫砂", "回应了物流问题"]
}
```

- 正文只允许使用白名单中的占位符（见 6.2），例如 `{{first_name}}`、`{{discount_code}}`、`{{unsubscribe_url}}`。
- `personalization_points` 用中文列出“这份文案针对客户做了哪些定制”，在审核界面展示，方便运营快速判断。

### 4.3 生成方式判定与小群划分

- **逐个定制**：`order_count >= 2`，或者有备注，或者有偏好标签（阈值写在店铺设置中）。
- **小群方式**：其余客户，按 `language + country + scenario + spend_tier + top_category` 分组；小群简报使用该组的统计特征（人数、主要品类、平均客单价），不包含任何单个客户的信息。小群文案中会使用 `{{last_product}}` 占位符，渲染时为每人填入他自己上次购买的商品。

### 4.4 模型路由

```ts
interface LlmProvider {
  id: 'openai' | 'deepseek' | 'doubao' | 'template';
  isConfigured(): boolean;     // 检查对应的环境变量是否齐全
  completeJson<T>(req: LlmJsonRequest<T>): Promise<LlmResult<T>>;
}
```

| 用途 | 默认链（可以通过环境变量覆盖） | 什么时候调用 |
| --- | --- | --- |
| `generate`（生成，含中文对照） | `<默认低价模型> → <另一个> → template` | 每个逐个定制的客户、每个小群各 1 次 |
| `premium_rewrite`（高质量重写） | `<高质量模型> → <默认低价模型> → template` | 销售点击“用高质量模型重写”时 |
| `review`（AI 检查） | `<默认低价模型> → 跳过` | 销售点击“帮我检查”时 |

- 默认低价模型在 M0 阶段通过对比选定（见 04 文档）。对比完成前，暂定 `deepseek → openai → template`。
- 链中会跳过未配置 Key 的供应商。供应商失败（超时、5xx 错误、输出不符合 schema 且重试 1 次仍失败）时，自动尝试下一个。
- 豆包通过把 `doubao` 写进链来启用。
- 每次调用都写入 `llm_calls`：用途、供应商、模型、是否降级、耗时、token 数、预估费用、错误摘要。**不记录 Key 和请求头。**
- `template` 供应商：根据“场景 × 语言 × 渠道”的模板，以及画像中的商品、品类、天数和推广优惠生成文案和中文对照。它不访问网络，也不理解备注。

### 4.5 预估与限流

- 预估调用次数 = 逐个定制人数 + 小群数（如果要求生成两个渠道，仍然是 1 次调用）。
- 预估 token 数按简报长度加输出上限估算；预估费用 = token 数 × 环境变量中配置的单价（没有配置单价时只显示调用次数和 token 数）。
- 并发数由 `LLM_CONCURRENCY` 控制（默认 4）；单批人数上限由 `OUTREACH_MAX_RECIPIENTS` 控制（默认 200）。

### 4.6 规则检查（免费，每份草稿都执行）

| 规则 | 级别 |
| --- | --- |
| 邮件正文缺少 `{{unsubscribe_url}}` 或 `{{company_address}}` | 阻止 |
| 出现白名单以外的占位符，或占位符没有闭合 | 阻止 |
| 文案语言与客户语言不一致（简单的语言检测） | 阻止 |
| 渲染时有必须填写的占位符没有值（例如没有折扣码却使用了 `{{discount_code}}`） | 阻止 |
| 邮件标题超过 80 个字符；WhatsApp 消息超过 1000 个字符 | 警告 |
| 命中夸大或违禁词表（英语和西班牙语） | 警告 |
| 备注中的隐私信息被遮盖过 | 提示 |

### 4.7 审核优先级

草稿按以下顺序排列，排在前面的标记为“需要重点看”：

1. 有阻止性问题。
2. 生成失败后由模板兜底，或者使用了备用模型。
3. 小群方式生成。
4. 有警告。
5. 其余（可以一键通过）。

## 5. 适配器

### 5.1 数据来源

```ts
interface DataSource {
  kind: 'shopify_csv' | 'shopify_api';
  parseCustomers(input: Readable): AsyncIterable<RowResult<NormalizedCustomer>>;
  parseOrders(input: Readable): AsyncIterable<RowResult<NormalizedOrder>>;
  parseAbandonedCheckouts(input: Readable): AsyncIterable<RowResult<NormalizedCheckout>>;
  parseProducts(input: Readable): AsyncIterable<RowResult<NormalizedProduct>>;
}
```

Shopify CSV 的要点（需要用真实导出文件核对）：

- 客户 CSV：`Customer ID`、`First Name`、`Last Name`、`Email`、`Accepts Email Marketing`、`Accepts SMS Marketing`、`Phone`、`Default Address Country Code`、`Tags`、`Note`。其中 `Note` 作为一条导入的备注。
- 订单 CSV：**每个商品占一行**，订单级字段只在第一行填写，需要按 `Name` 合并；订单中**没有客户 ID**，需要用 `Email` 关联客户。关键字段包括 `Name`、`Id`、`Email`、`Financial Status`、`Created at`、`Currency`、`Total`、`Discount Code`、`Lineitem name`、`Lineitem sku`、`Lineitem quantity`、`Lineitem price`、`Shipping Country`。
- 退款或取消的订单不计入消费和转化。
- 列名匹配时忽略大小写和首尾空格；无法识别的列在预览中列出，但不报错。
- 以后接入 Shopify API 时，只需要新增 `shopify-api` 适配器，输出相同的标准结构。

### 5.2 邮件发送

```ts
interface EmailSender {
  id: 'mock' | 'smtp';
  send(msg: OutgoingEmail): Promise<SendResult>;   // OutgoingEmail 含 List-Unsubscribe 头
}
```

- `mock`（默认）：不访问网络，写入 `messages` 表并标记为送达；根据收件人 ID 的哈希生成确定性的模拟打开和点击数据；界面上标注“模拟发送”。
- `smtp`：设置 `EMAIL_SENDER=smtp` 和 SMTP 相关变量后启用。
- 发送在进程内队列中按限速执行；单封失败不影响其他邮件。

### 6.3 接口清单

除标注“不在 `/api/v1` 下”的接口外，下表路径都带 `/api/v1` 前缀。除登录、退订、追踪和健康检查外，所有接口都需要登录（Cookie 会话）。错误响应统一为 `{ error: { code, message, details? } }`；列表接口的返回格式为 `{ items, total }`。

**账号与店铺**

| 名称 | 方法与路径 | 说明 |
| --- | --- | --- |
| login / logout / me | `POST /auth/login`、`POST /auth/logout`、`GET /auth/me` | 登录、退出、当前用户和店铺 |
| getStore / updateStore | `GET` / `PATCH /store` | 品牌、发件人、公司地址、语言映射、复购周期、“信息充足”阈值 |

**导入与客户**

| 名称 | 方法与路径 | 说明 |
| --- | --- | --- |
| previewImport | `POST /imports/preview`（multipart，`kind`） | 返回批次 ID、计数、错误行、未识别的列 |
| commitImport | `POST /imports/:batchId/commit` | 确认入库，返回新增数和更新数 |
| listImports | `GET /imports` | 导入批次列表 |
| listCustomers | `GET /customers?q=&country=&language=&tier=&category=&tag=&type=&hasNotes=&page=` | 客户列表（含画像摘要） |
| getCustomer | `GET /customers/:id` | 画像、订单、备注、收到过的推广 |
| updateCustomer | `PATCH /customers/:id` | 修改偏好标签、客户类型、语言 |

| deleteCustomer | `DELETE /customers/:id` | 删除单个客户（含备注） |
| purgeStoreData | `POST /privacy/purge` | 需要输入店铺名确认；清空客户、订单、备注、推广数据 |

**挑选客户与营销节点**

## 10. 主要风险与对策

| 风险 | 对策 |
| --- | --- |
| 逐个定制的费用和耗时 | 每人 1 次调用；信息少的客户走小群方式；默认低价模型；生成前显示预估；单批上限 200；并发可配置 |
| 文案千篇一律，看不出定制 | 提示词要求引用画像中的具体信息；输出 `personalization_points`；审核界面展示定制要点；验收中抽查 |
| 备注泄露隐私 | 保存时提醒，发送给模型前遮盖；简报类型上不包含个人信息字段；用测试断言 |
| 模型输出不稳定或超时 | 用 JSON schema 校验，重试 1 次，然后按模型链降级，最后由模板兜底；单个失败不影响整批 |
| 真实的 Shopify 导出格式与预期不同 | 列名宽松匹配并支持别名；预览中列出未识别的列；试用前用真实文件核对 |
| 模拟数据被误认为真实效果 | 模拟事件带 `simulated` 标记，报表中标注 |
| 三个子 Agent 并行时冲突 | 严格按目录划分归属；shared 只由主 Agent 修改；CI 检查路径归属 |
| 泄露密钥 | 只从环境变量读取；CI 扫描密钥特征串；日志脱敏 |
