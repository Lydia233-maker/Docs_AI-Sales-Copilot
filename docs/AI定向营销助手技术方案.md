# AI 定向营销助手技术方案

> 版本：V1（第一版，可试用版）
> 依据：[01 产品定位与需求](./01-产品定位与需求.md) 中已确认的需求
> 状态：**已确认采用**（2026-10-11）：TypeScript 前后端分离 + SQLite
> 关系说明：本文用大白话解释方案和取舍；详细的接口、表字段和目录结构以 [02 技术方案与目录结构](./02-技术方案与目录结构.md) 为准，开发任务见 [任务清单](./AI定向营销助手任务清单.md)。

## 0. 先用一段话说清楚要做的系统

卖家把 Shopify 导出的客户和订单表格交给系统。系统给每位客户建一张“客户档案卡”，销售还可以在卡片上写备注。销售挑出一批客户、用中文写一句推广意图后，系统按每张档案卡**给每位客户单独写一封信**：用客户的语言写，同时附中文翻译。销售审核后，系统帮忙寄出（默认是“假装寄出”，用于演示），或者由销售复制后自己发。之后再导入新订单，系统统计有多少人因此下了单。

方案必须满足下面几条硬要求：

| 硬要求 | 来源 |
| --- | --- |
| 每个客户一份独立文案，信息少的客户可以按小群生成 | 需求 4.4 |
| 每个客户最多调用 1 次模型，默认使用低价模型（暂定 DeepSeek） | 需求第 6 节 |
| 没有 Key、没有网络也能完整演示 | 需求第 6 节 |
| 退订链接、只发给同意营销的客户、数据可删除 | 需求第 5 节 |
| 发给模型的数据不含姓名、邮箱、手机号 | 需求 4.4 |
| 数据接入可以替换（以后接 Shopify API） | 需求 4.1 |
| 3 个子 Agent 能按目录分开并行开发 | 04 文档 |

## 1. 方案：TypeScript 前后端分离 + SQLite

### 1.1 技术选型及原因

| 部分 | 选型 | 为什么 |
| --- | --- | --- |
| 仓库组织 | pnpm workspace 单仓库 | 前端、后端、共享类型、测试放在一个仓库，但分成独立目录，正好对应 3 个子 Agent 的分工 |
| 语言 | TypeScript（前后端都用） | 前后端可以共用同一份类型定义，改一处，两边都有提示 |
| 前端 | React + Vite | 生态最大、资料最多；Vite 启动快 |
| 前端组件 | Ant Design | 中文后台组件齐全（表格、表单、抽屉、进度条），不用自己画 |
| 前端数据请求 | TanStack Query | 自动处理加载中、刷新、缓存，方便实现“生成进度”轮询 |
| 后端 | Node.js + Fastify | 比 Express 快，自带请求校验，TypeScript 支持好 |
| 共享类型和校验 | Zod（放在 `packages/shared`） | 一份定义同时用于前端表单校验、后端请求校验和 TypeScript 类型 |
| 数据库 | SQLite + better-sqlite3 + Drizzle ORM | 一个文件就是整个数据库，不需要单独装数据库服务；Drizzle 写法接近 SQL，迁移清楚 |
| CSV 解析 | papaparse | 支持流式读取大文件，能处理带引号和换行的字段 |
| 大模型 | 直接用 `fetch` 调用 OpenAI 兼容接口 | DeepSeek、GPT、豆包都兼容这个协议，一份代码换个地址就能切换，不依赖某一家的 SDK |
| 邮件 | 模拟发送（默认）+ nodemailer（SMTP） | SMTP 是通用标准，卖家用哪家邮件服务都能接 |
| 测试 | Vitest（单元测试）+ Playwright（端到端测试） | 速度快，和 Vite、TypeScript 配合好 |
| 部署 | Docker 单镜像 | 后端同时提供前端页面，一个容器、一个端口、一个数据库文件，最省事 |

### 1.2 架构

```
                    ┌──────────────────────────────────────────┐
  卖家浏览器  ───►  │  前端 apps/web（React，中文界面）          │
                    └───────────────┬──────────────────────────┘
                                    │ HTTP（数据格式由 packages/shared 规定）
                    ┌───────────────┴──────────────────────────┐
                    │  后端 apps/api（Fastify）                  │
                    │                                          │
                    │  ① 导入   ② 档案与备注   ③ 挑选客户          │
                    │  ④ 推广与生成任务   ⑤ 检查与审核             │
                    │  ⑥ 发送 / 复制 / 导出   ⑦ 追踪转化   ⑧ 删除   │
                    │                                          │
                    │  可替换的“插头”：                          │
                    │   数据来源：Shopify CSV │（以后）Shopify API │
                    │   大模型：DeepSeek │ GPT │ 豆包 │ 模板       │
                    │   邮件：模拟发送 │ SMTP                    │
                    └───────┬───────────────────────┬──────────┘
                            │                       │
                     SQLite 数据库文件         外部服务（都是可选的）
```

**数据怎么流转：**

1. **导入**：CSV → 解析并逐行校验 → 预览 → 确认 → 写入客户、订单表 → 重新计算每个客户的档案（订单数、消费、品类偏好等）。
2. **补充**：销售在档案上添加备注和偏好标签；保存时检查备注中是否有邮箱、电话。
3. **挑选**：场景、条件、手动勾选 → 得到一份名单（≤ 200 人）→ 创建推广时把名单“冻结”保存下来。
4. **分流**：信息充足的客户逐个定制；信息少的客户按“语言 + 国家 + 场景 + 消费层级 + 主要品类”分成小群。
5. **生成**（后台慢慢做）：给每个客户（或小群）做一份“简报”，去掉姓名、邮箱、手机号，再交给模型；模型一次返回外语文案和中文对照；然后经过规则检查，保存为这个客户的草稿。
6. **审核**：有问题的排在前面；其余可以一键通过。
7. **发出**：把姓名、退订链接等填进草稿，再交给邮件“插头”；或者给销售复制；或者导出 WhatsApp 文件。
8. **追踪**：记录打开、点击、退订；导入新订单后，统计 7 天内下单的客户。

### 1.3 数据结构草图

完整字段见 02 第 7 节，这里只列核心表之间的关系：

```
stores 店铺 ─┬─ users 账号
             ├─ customers 客户 ─┬─ customer_notes 销售备注
             │                  ├─ customer_profiles 档案（自动计算）
             │                  └─ orders 订单 ── order_items 订单商品
             ├─ checkouts 弃单、products 商品、import_batches 导入记录
             └─ outreach 一次推广 ─┬─ outreach_recipients 冻结的名单（每人一行）
                                   ├─ cohorts 小群
                                   ├─ drafts 草稿（每个收件人一份）★核心
                                   ├─ jobs 后台任务（生成、发送）
                                   ├─ messages 已发出的消息 ── message_events 打开、点击、退订
                                   └─ conversions 转化
llm_calls 模型调用记录、audit_logs 操作日志
```

最核心的一张表是 `drafts`：

| 字段 | 含义 |
| --- | --- |
| recipient_id | 写给谁（指向冻结名单中的某个人） |
| mode | 逐个定制，还是小群方式 |
| email / whatsapp | 外语文案（含占位符） |
| zh | 中文对照 |
| personalization_points | 中文列出“针对这个人定制了什么” |
| checks / priority | 检查结果、审核时的排序 |
| status | 生成中 / 已生成 / 失败 / 已通过 / 已驳回 |
| provider / model / is_fallback | 由哪个模型写的，是否是备用模型 |

### 1.4 主要技术和工具

React、Vite、Ant Design、TanStack Query、MSW；Node.js、Fastify、Zod、Drizzle、better-sqlite3、papaparse、nodemailer；Vitest、Playwright；pnpm、Docker、GitHub Actions。

### 1.5 优缺点和取舍

**优点**

- **最简单**：一个容器、一个数据库文件就能跑起来；给试用卖家部署、备份（复制一个文件）都很容易。
- **前后端共用一份类型**：接口字段改了，前端、后端、测试同时报错提示，不会悄悄出错。
- **分工最清楚**：web、api、e2e 三个目录对应 A、B、C 三个子 Agent，互不干扰。
- **离线可演示**：模板、模拟发送都在本地完成。

**缺点**

- **SQLite 只适合单台服务器**：同一时间只能有一个写操作。几个试用卖家完全够用；以后同时在线的卖家很多时，需要换成 PostgreSQL。
- **后台任务放在进程内**：服务器重启时，正在生成的任务会中断，需要在启动时把它们标记为“可重试”。
- **Node.js 做数据分析不如 Python 方便**：不过第一版的统计（RFM、复购间隔）都很简单，影响不大。

**取舍**：第一版的目标是让 3～5 个卖家用起来，“简单、好部署、好分工”比“能撑大规模”更重要。代码里通过 Drizzle 和“插头”把数据库和外部服务隔离开，以后换 PostgreSQL 或加独立队列，不需要推倒重来。

### 1.6 以后的升级路线

1. **数据库**：所有数据库操作都通过 Drizzle，并且每个查询都带 `store_id`。以后把 SQLite 换成 PostgreSQL，主要改连接配置和少量 SQL 写法。
2. **后台任务**：生成和发送都通过 `jobs` 模块提交任务，业务代码不直接依赖队列的实现方式。以后可以把进程内队列替换成 Redis 队列。

### 1.7 大白话：这个方案在做什么

可以把它想成一家**小型代写信件工作室**：

- **前台**（前端）：销售坐在这里，翻客户档案、挑人、看稿子、点“寄出”。
- **后厨**（后端）：真正干活的地方，负责整理档案、写信、检查、寄信。
- **一个文件柜**（SQLite）：所有档案和信件都放在里面，搬家时把整个柜子抱走就行。
- **一本双方都认的点菜单**（`packages/shared`）：前台点什么菜、后厨上什么菜，都按这本菜单来；菜单只有店长（主 Agent）能改。
- **三个插头**：数据从哪来、请谁写信、用什么寄信，都插在插头上。今天插的是“表格”“DeepSeek”“假装寄出”，以后换成“Shopify 接口”“GPT”“真邮局”，拔下来再插上就行，墙不用拆。
- **写信的规矩**：写信的人（AI）只看到“这位客户买过什么、喜欢什么、销售说过什么”，看不到他的名字和联系方式；名字最后由前台自己填上。

## 2. 以后自己改代码时特别容易踩的坑

按“踩到的后果有多严重”排序：

| # | 坑 | 后果 | 怎么避免 |
| --- | --- | --- | --- |
| 1 | **新增了一个发送或导出的入口，却忘了过滤“未同意营销 / 已退订 / 已删除”的客户** | 违反合规，可能被投诉或被邮件服务商封号 | 所有发送、复制、导出都必须调用同一个“取可触达收件人”函数，不要自己写查询；验收测试 C4 会检查 |
| 2 | **给模型的简报里加字段时，顺手把整个客户对象传了进去** | 姓名、邮箱、手机号被发给第三方模型 | 简报只能通过 `generation/brief.ts` 构建，它的类型中没有个人信息字段；不要使用 `...customer` 展开整个对象；测试 C10 会检查 |
| 3 | **新增了一张和客户有关的表，却没有加到删除逻辑里** | “删除客户”后数据还残留，合规不达标 | 新增与客户有关的表时，同步修改 `privacy/delete.ts`，并补充测试 C7 |
| 4 | **新写的查询忘了带 `store_id`** | A 卖家看到 B 卖家的客户 | 数据库操作统一放在各模块的 `repo` 中，并且都要求传入 `store_id`；测试 K4 会检查 |
| 5 | **只改了前端或后端，没有改 `packages/shared`**（或者反过来） | 页面报错，或者字段静默变成空值 | 接口字段只在 shared 中定义；改完后在根目录执行 `pnpm build`，类型不一致会直接报错 |
| 6 | **直接修改数据库表结构，没有生成迁移文件**，或者为了省事删掉数据库文件重来 | 线上的试用数据丢失，或者新旧版本对不上 | 改了 `db/schema.ts` 后，必须执行 drizzle-kit 生成迁移文件并一起提交；上线前先备份 SQLite 文件 |
| 7 | **改占位符时只改了一处** | 发出去的邮件中出现 `{{frist_name}}` 这样的原样文字 | 占位符白名单在 shared 中；新增或修改占位符时，同时更新白名单、渲染函数和检查规则；规则检查会拦截白名单以外的占位符 |
| 8 | **修改提示词后，所有文案的风格都变了，但没有察觉** | 质量下降，或者模型返回的格式变了导致解析失败 | 提示词文件带版本号；修改后用 fixtures 中的 10 位客户跑一遍对比；模型输出必须经过 schema 校验 |
| 9 | **金额使用小数（浮点数）计算** | 出现 0.1 + 0.2 ≠ 0.3 这样的误差，报表金额对不上 | 金额统一以“分”为单位，用整数存储和计算，只在显示时换算 |
| 10 | **日期和时区处理不一致** | “沉睡 60 天”“7 天内转化”在边界上算错一天 | 数据库统一存 UTC；“距今天数”按店铺时区计算；边界情况有单元测试（A2） |
| 11 | **测试或演示时误配置了真实 SMTP** | 演示邮件被发给真实客户 | 默认是模拟发送；演示数据只使用 `example.com` 邮箱；真实发送需要同时设置 `EMAIL_SENDER=smtp` 并填写公司地址 |
| 12 | **把 API Key 写进代码，或者提交了 `.env` 文件** | Key 泄露，被别人盗用产生费用 | Key 只放在环境变量中；`.env` 已加入 `.gitignore`；CI 会扫描密钥特征串 |
| 13 | **以为 SQLite 能多开几个后端进程** | 数据库被锁，出现“database is locked” | 第一版只运行一个后端进程；需要扩容时换成 PostgreSQL |
| 14 | **服务器重启后，“生成中”的任务一直卡住** | 页面进度永远不动 | 后端启动时把未完成的任务标记为“已中断，可重试”（B 的实现要求） |
| 15 | **按 Shopify 订单 CSV“一行就是一笔订单”来理解** | 订单数和金额翻倍 | 订单 CSV 中每个商品占一行，必须按订单号合并；订单通过邮箱关联客户，邮箱比较前要统一转为小写并去掉空格 |

其中 **1～4 是合规和数据安全相关的坑**，踩到的代价最大。修改相关代码后，务必在根目录运行一次 `pnpm acceptance`，确认合规条目 C1～C10 全部通过。
