# 画像定向技术方案

> 依据：[画像定向需求文档V1](./画像定向需求文档V1.md)。只覆盖那一版已经说定的范围。
> 现有代码是 pnpm 仓库里的 React 页面、Fastify 接口和一份 SQLite 账本。三个方案都从这份代码出发，不另起一套产品。
> 推荐 **方案一**。方案二留到真要多店、多进程的时候。方案三能跑，但不适合把客户资料交给浏览器。

## 方案一：在现在这家店的后厨里写信

### 在做什么

把现在的演示店想成一家小店。前台还是现在的网页。后厨还是现在这个后端进程。账本还是硬盘上那一个 SQLite 文件。

差别是：后厨不再只用一张固定信纸填空。运营写好这场想说什么之后，后厨先算要写多少封、大概花多少钱，再一封一封交给 DeepSeek 写。写一封就在账本上记一笔，页面上能看到写到第几封。DeepSeek 写失败，就换回现在这张信纸。没有钥匙（API Key）时，从一开始就用信纸，演示不用联网。

聊天不直接进信。Gorgias 的表格先变成「这个邮箱说过这句话」。后厨从话里抽出偏好和需要小心的事，放在待确认的篮子里。销售点头之后，才允许写进信。

### 技术选型

| 用什么 | 为什么 |
| --- | --- |
| 继续用 TypeScript、React、Vite、Fastify | 页面、登录、审核、模拟发送已经在这上面。换框架等于把店拆了重建 |
| 继续用 SQLite（better-sqlite3） | 两千到三千个客户对一个文件账本很小。这一版不做服务器部署，不必为了规模换数据库 |
| 继续用 Zod（`packages/shared`） | 发给模型的客户简报要挡住姓名、邮箱、电话。规则放在共享包里，页面和后厨用同一份 |
| DeepSeek 用 HTTPS 直接调用，协议按它公开的对话接口 | 需求指定默认模型是 DeepSeek。不经过 OpenAI。失败就用现有的 `templates.ts` |
| 不用新的队列软件、不用 Redis | 生成进度写在 SQLite 里就够。多一个软件，这台机器就要多养一个服务 |
| CSV 继续用现在的解析 | 客户和订单已经按 Shopify 表头解析。弃单和 Gorgias 各加一个读取器，不换整套解析库 |

### 数据怎么走

```
网页上传三张表（客户、订单、弃单）和一张 Gorgias 表
        │
        ▼
后厨先整张表检查，通过了再写入账本，并重算画像
        │
        ▼
网页按场景和条件挑人，可以勾上或去掉个别人
        │
        ▼
后厨冻结名单，算出「单独写几封、共用几封、大约几次调用、大约多少钱」
        │
        ▼
后厨在自己进程里慢慢写。每写完一封就更新进度。进度显示在推广列表和这场的审核页上，不要求销售去看数据库文件。
        │
        ▼
销售看事实和中文对照，可以改这一封，也可以只重写这一封
        │
        ▼
模拟发送：只发已通过、且同意营销的信。姓名和地址在这一步才填进去
```

两千到三千人按模型实际速度写完，不设 10 分钟期限。页面不要干等那一个请求结束，要能离开再回来看进度。

中途停下时，销售看的地方是网页，不是账本文件。推广列表上这场显示「中途停下」。点进去的审核页顶部写着：计划多少封、已经写完多少封、还没写的从哪一封开始、失败几封。下面仍是已经写好的信。按钮「继续写剩下的」只补未完成和失败的。后端重新启动时，把还标着「正在写」的场次改成「中途停下」，列表里马上能看见。

### 数据结构草图

在现有客户、订单、推广、草稿、消息表上加这些，不把旧表推倒重来。

| 账本里的一格 | 记什么 |
| --- | --- |
| 客户上已有的 `language_overridden` | 销售改过语言就标 1。再次导入时，这一位的语言不再按国家重猜 |
| 店铺上的公司地址 | 页面改的就是这一格。信的底部用它 |
| 弃单、弃单商品 | 谁、何时、哪件商品没买成。没有这张表时，弃购挽回直接告诉用户「还没有弃单数据」 |
| 事实 | 一位客户的一条「偏好」或「需要小心的事」。状态是待确认或已确认。来源是客户表 Note、商品标题，或 Gorgias。旁边留原话。只有已确认的能进信 |
| 生成任务 | 状态是正在写、已写完或中途停下。记下计划封数、已写完封数、下一封还没写的是谁、失败封数，以及用的是模型还是信纸。后端一启动，把仍标成「正在写」的任务改成「中途停下」 |
| 收件人上已有的单独写 / 共用 | 买过至少两次，或已有确认过的事实，就单独写。否则按语言、国家、场景、消费层级、主要品类合成一群，共用一封，再填各自的姓名和上次商品 |

聊天入口只做一件事：把某种导出读成「邮箱 + 原话」的列表。这一版的读取器只认识 Gorgias 报表里的「Export with message content」。以后换别的客服工具，只加一个新的读取器，抽取、确认、写信都不改。

商品标题的提议也进同一张事实表，来源标成「标题」，状态是待确认。页面上不提供手写备注或手写标签的入口。客户 CSV 的 Note 是店里已经写过的话，导入后可以作为事实来源；其中的邮箱和电话先遮盖，再送给模型。

费用：调用次数等于「单独写的人数 + 共用信的群数」。单价从环境变量读。没有单价时显示次数，并写明费用还没配置，不编一个数字。

### 优缺点

好处是改动都长在现有店里。登录、占位符、模拟发送、演示数据可以留着。两千到三千行 CSV 用一个文件账本读写得过来。没有新的服务要安装。

代价是写信的时候这一个后端进程比较忙。进程如果中途停了，销售在推广列表看到这场是「中途停下」，点进审核页能看到已经写完的信，以及还没写的从哪一封开始。页上可以继续写剩下的。SQLite 同时只能好好伺候一个写账本的进程，不能再开第二个后端对着同一个文件写。

## 方案二：后厨搬到另一间房

### 在做什么

前台和账本的用法跟方案一一样。差别是写信的人不住在接待客人的那个进程里，而是单独一个工人。接待处把「这场要写的名单」放进一条队伍，工人拿走再写，写完把信放回账本。页面仍然只看进度。

打个比方：方案一是店员一边看柜台一边在后厨写信。方案二是柜台只接单，信交给隔壁房间的人写。隔壁房间即使忙很久，柜台还能开门。

### 技术选型

| 用什么 | 为什么 |
| --- | --- |
| 网页和接口仍是现在的 React 和 Fastify | 前台不用因为后厨搬家而重做 |
| 账本换成 PostgreSQL，或继续 SQLite 但工人和接口不能同时硬写 | 两个进程同时写同一个 SQLite 文件容易锁住。要真拆开，账本就得换成能让多人一起写的数据库 |
| 队伍用数据库里的一张「待写」表，或用 Redis 这类专门排队的软件 | 工人要知道下一封写谁。用账本排队少一个软件；用 Redis 排队更稳，但要多安装一个 |

### 数据怎么走

和方案一相同，只是「慢慢写」发生在另一个进程。接口负责上传、挑人、报价、审核和模拟发送。工人只负责调用 DeepSeek 和把草稿写回账本。

### 数据结构草图

和方案一那几格相同。多一张待写队列：这场、哪一位客户或哪一群、第几次尝试、成功还是失败。

### 优缺点

好处是接口进程不会被两千多次模型调用拖住。以后真要部署、要同时开两家店，这条路更稳。

代价是这一版就要多一个进程，多一套启动方式。SQLite 的文件锁会变成每天都能遇到的问题，所以几乎一定会把数据库也换掉。需求里这一版明确不做阿里云部署，也没有第二家店。为了三千封信先把地基换了，不划算。

## 方案三：让浏览器直接去求 DeepSeek

### 在做什么

网页把客户简报从后厨拿回来，由浏览器自己请求 DeepSeek，写好再交回后厨保存。后厨只当仓库。

打个比方：信纸和客户档案都锁在店里，却让每位店员用自己手机上的钥匙去找代笔。钥匙会进到浏览器里，换一台电脑、开一次调试工具就能看见。

### 技术选型

网页仍是 React。浏览器里用 `fetch` 调 DeepSeek。草稿仍存回 Fastify 和 SQLite。

### 数据怎么走

后厨只提供不含姓名的简报。浏览器写信。后厨收草稿、做审核和模拟发送。

### 优缺点

好处是模型调用不占后厨的时间，进度天然在页面上。

代价是 API Key 必须出现在浏览器能拿到的地方。这和「钥匙只放在服务器环境里」相反。客户简报虽然没有姓名，仍然是购买记录和备注，不该在每个店员的浏览器里转一圈再出去。这一版不采用。

## 建议采用哪一个

采用方案一。

现有代码、演示店和审核流程都能接着用。三千个客户的难处在 DeepSeek 的速度，不在数据库。进度放在 SQLite 里，页面轮询或再次打开就能看见。方案二的拆分等真要部署、真有第二家店时再做，到时候聊天读取器和事实表都不用推翻。

## 以后改代码时容易踩坑的地方

这些都是方案一里，改错一行就会让人数、信的内容或隐私和需求对不上的地方。

1. **改了表结构，旧账本不会自己长出新列。** 现在建表用的是「没有这张表才创建」。已经存在的 `apps/api/data/app.db` 不会自动加上弃单、事实、生成任务这些列。改完要重新灌演示数据，或另写一段补列。从别的目录启动后端，会在另一个位置新建一本空账本。

2. **`pnpm seed` 会清空整本账本再重建演示店。** 不只删一家店的业务数据。手里正在看的导入、确认过的事实和推广都会没。

3. **订单表一行是一件商品，不是一笔订单。** 合并错了，购买次数和金额会翻倍。客户和订单用小写邮箱对上。金额用「分」的整数存，显示时再除以 100。

4. **再次导入不能覆盖销售改过的语言。** 列 `language_overridden` 已经在表上，但现在没有任何写入。导入时先看这个标记，再决定要不要按国家重猜语言。

5. **发给模型的包里不能有姓名、邮箱、电话。** 姓名只允许在复制和模拟发送时，用 `{{first_name}}` 填回去。现在的生成代码是手工组装这个包，没有拿共享的简报规则去卡。接上 DeepSeek 之后必须先卡住，再发出去。备注和聊天原话里的邮箱、电话要先遮盖。

6. **中文意图不能原样贴进外语信。** 现在的信纸会把中文意图拼进英文正文。换模型时如果失败回退到这张信纸，回退结果也要改成「写成优惠说明」，不能把旧行为带回去。有折扣码仍写 20% off，不要从「8 折」里自己换算。

7. **没有额外事实的人要先分组，再数调用次数。** 费用显示的次数是「单独写的人数 + 群数」，不是客户人数。先按人各写一封再去显示费用，页面上的钱会对不上。分组按语言、国家、场景、消费层级、主要品类，这是 `docs/01` 里已经确认的分法。

8. **待确认的事实不能进信。** 商品标题提议和 Gorgias 抽出的句子，默认都是待确认。确认前参加挑选可以，参加写信不行。页面上不要再做「添加备注」「添加标签」的入口。

9. **Gorgias 只认带消息正文的那一种导出，并且只用邮箱对客户。** 不带正文的导出、对不上邮箱的行，都不能算到某位客户头上。这种导出只有最近 30 天。读取器不要写成「看见 CSV 就当聊天记录」。别的客服工具以后加读取器，不要在写信逻辑里写死 Gorgias 的列名。

10. **没有正文的提交不要带 JSON 头。** 现在的前端只在有正文时才加这个头。生成、模拟发送如果又加上空的 JSON 头，接口会直接拒绝。

11. **接口用驼峰，账本列用蛇形。** 只改一边，页面会拿到空字段。`/api/v1/auth/me` 和 `/api/v1/store` 的地址目前仍是 `company_address`。做「页面上改地址」时要一起改返回字段和网页里的类型，网页并没有引用共享包。

12. **能否发送只走现有的资格判断。** 新写的挑选、复制、模拟发送都不能自己再查一遍同意状态。未同意的人可以出现在名单里，不能生成，也不能发送。退订页面这一版不做，但信里仍要留退订链接占位符；不要写成已经有人点开就会被记成退订。

13. **钥匙不要写进代码、文档或日志。** 程序现在不会自动读 `.env` 文件。DeepSeek 的 Key 和单价要在启动后端的那个进程里设好。只写在 `.env` 里不会生效。

14. **弃单 CSV 的列名先用一份真实导出核对。** 需求只定了「最近 1 到 7 天的弃单，且之后没有下单」。列名没在需求里定死，不要照订单表头猜。

15. **同一时间只跑一个后端进程。** 生成任务跑着的时候再开一个，SQLite 会锁，进度会写乱。
