## 1. 角色与边界

| 角色 | 职责 | 唯一可以修改的路径 | 对应的验收条目 |
| --- | --- | --- | --- |
| **主 Agent** | 定接口、搭仓库骨架、准备演示与契约数据、做模型对比、审查与合并 PR、协调接口变更、维护文档 | `packages/shared/`、`docs/`、`fixtures/`、`scripts/`、`.github/`、根目录配置文件（`package.json`、`pnpm-workspace.yaml`、`pnpm-lock.yaml`、`tsconfig.base.json`、lint 配置、`.env.example`、`.gitignore`、`Dockerfile`、`docker-compose.yml`、`README.md`） | G3、G4、K1、K2、M11、Y1、Y4 |
| **Agent A：前端** | 卖家使用的全部中文界面 | **只能修改 `apps/web/`** | G6，以及 N、A、H、P、M、R、E、T、C 中标注为 E2E 的界面部分；各页面的组件测试 |
| **Agent B：后端** | API、导入、画像与备注、挑选客户、生成任务、模型路由、检查、审核、发送、追踪、合规、删除、脚本 | **只能修改 `apps/api/`** | D、N、A、H、P、M、R、E、T、C、K3～K5、Y2、Y3 的实现和单元测试 |
| **Agent C：端到端测试与验收** | 端到端测试、接口契约与合规测试、伪造的外部服务、一键验收报告、演示录屏 | **只能修改 `tests/e2e/`** | 03 中所有标注为 E2E 和 API 的条目，以及第 14 节的演示 |

硬性规则：

1. **子 Agent 之间不能修改对方的文件**，也不能修改主 Agent 的文件（第 5 节允许的 `pnpm-lock.yaml` 变化除外）。
2. **接口（`packages/shared`）只能由主 Agent 修改。** 子 Agent 不能在自己的目录中复制或重新定义接口类型来绕开这条规则。
3. 每个子 Agent 在**独立的 git worktree 和独立的分支**上工作。
4. 违反路径归属的 PR 会被 CI 中的归属检查拦截。

### M0：接口、骨架与模型对比（主 Agent）

主 Agent 完成以下内容，合并到 `main` 后 A、B、C 才开始工作：

1. **仓库骨架**：根目录的 `package.json`（脚本：`dev`、`build`、`test`、`lint`、`e2e`、`acceptance`）、`pnpm-workspace.yaml`、`tsconfig.base.json`、lint 和格式化配置、`.gitignore`、`.env.example`（只有变量名）。
2. **`packages/shared` 第一版完整接口**：02 第 6 节中的全部枚举、占位符白名单、错误码、各领域的 Zod schema 和 `api.ts` 接口清单，附 schema 单元测试和 `CHANGELOG.md`。
3. **三个应用的最小空壳**：`apps/web`、`apps/api`、`tests/e2e` 各自的 `package.json`、`tsconfig.json` 和空入口，预先安装计划使用的依赖，让 lockfile 基本稳定。**M0 合并后，这三个目录的归属分别转交给 A、B、C。**
4. **`fixtures/`**：宠物用品演示数据（Shopify 格式的客户、订单、弃单、商品 CSV，演示备注 `notes.json`，发送后订单 `orders_after_send.csv`），错误样例，以及 `fixtures/demo-pet/README.md`。说明文件中写明：各场景的期望人数、指定客户的期望画像、期望的生成方式（逐个定制或小群方式）、期望的小群划分和期望的转化结果。
   - 规模约 300 位客户、900 笔订单。覆盖英语和西班牙语国家、5 个场景、3 个消费层级；包含有备注和偏好标签的熟客、只下过一单的新客、未同意营销的客户、手机号无效的客户、带 `lang:` 标签的客户、多商品订单、退款订单，以及备注中带有邮箱或电话的客户（用于测试隐私遮盖）。
5. **模型对比**（`scripts/model-benchmark/`，需要负责人提供 Key）：
   - 从演示数据中选 10 位画像各不相同的客户，用同一份生成提示词，分别在候选模型上生成（GPT 的低价小模型、DeepSeek；如果配置了豆包，也一起比较）。
   - 记录每个模型的价格、耗时、JSON 格式成功率；由主 Agent 按“外语是否地道、是否用上了画像和备注、中文对照是否准确”打分，把样例全文提交给负责人抽查。
   - 结论写入 `docs/model-benchmark.md`，包括选定的默认模型、备用模型、高质量模型，以及 200 位客户的预估费用。B 实现时以这份提示词为起点。
   - **如果没有 Key**：跳过对比，暂定 `deepseek → openai → template`，等提供 Key 后补做。
6. **CI**：`.github/workflows/ci.yml` 运行安装、构建、lint、测试、密钥扫描（`scripts/scan-secrets.mjs`），以及路径归属检查（`scripts/check-ownership.mjs`）。

## 3. Worktree 与分支

主 Agent 在 M0 合并后创建三个 worktree，分别交给三个子 Agent：

```bash
git fetch origin main
git worktree add ../copilot-a-web -b cursor/agent-a-web-0805 origin/main
git worktree add ../copilot-b-api -b cursor/agent-b-api-0805 origin/main
git worktree add ../copilot-c-e2e -b cursor/agent-c-e2e-0805 origin/main
```

- 分支名格式为 `cursor/agent-<a|b|c>-<范围>-0805`，全部小写。一个 Agent 有多个 PR 时，每个 PR 单独开分支，例如 `cursor/agent-b-api-generation-0805`。
- 所有 PR 的目标分支都是 `main`，默认以草稿形式创建；满足 03 第 1 节的通用标准后，再标记为可审阅。
- 同步上游时只能 **rebase 到 `origin/main`**，不能合并其他子 Agent 的分支。
- 提交信息使用 `feat(web|api|e2e):`、`fix(...)`、`test(...)`、`chore(...)` 前缀；每个逻辑上独立的改动单独提交。
- 只有主 Agent 可以合并 PR。

## 4. 接口变更流程

1. 子 Agent 发现 shared 中的接口不够用或有错误时，**不能自行修改**，也不能在自己的目录里临时定义替代类型。
2. 在自己 PR 的描述中增加“接口变更请求”小节，写明：涉及的接口、现状、期望的修改、原因，以及对其他 Agent 的影响。新接口合并之前，可以用 `// TODO(shared-change): <请求标题>` 标记临时的绕行代码。
3. 主 Agent 评估后，单独提交一个 shared PR，同时更新 02 第 6 节和 `packages/shared/CHANGELOG.md`。修改不兼容时，在 PR 中写明 A、B、C 各自需要做的修改。
4. 合并后，主 Agent 在受影响的子 Agent PR 中评论，通知 rebase。
5. M1 期间，主 Agent 优先只做**向后兼容**的修改（新增字段、新增接口）。

## 5. 共享资源规则

| 资源 | 规则 |
| --- | --- |
| `pnpm-lock.yaml` | 由主 Agent 所有。子 Agent **只能**在自己的 `package.json` 中新增依赖，并提交由此产生的 lockfile 变化，同时在 PR 中说明新增依赖的用途。发生 lockfile 冲突时，由主 Agent 在合并时重新执行 `pnpm install` 解决 |
| 根目录脚本、`.env.example` | 由主 Agent 所有。子 Agent 需要新增脚本或环境变量时，通过接口变更请求提出 |
| `fixtures/` | 由主 Agent 所有。C 需要的额外边界数据放在 `tests/e2e/fixtures/`；B 的私有测试数据放在 `apps/api/test/fixtures/` |
| 提示词 | 主 Agent 在 M0 的模型对比中提供第一版生成提示词；之后由 B 在 `apps/api/src/data/prompts/` 中维护，修改时需要写明版本号 |
| 端口 | API 使用 3000，Web 开发服务器使用 5173；C 的测试使用 3100 和 5273；伪造的大模型服务使用 3901，伪造的 SMTP 服务使用 3902 |

路径归属检查（`scripts/check-ownership.mjs`）：根据分支前缀 `cursor/agent-a-*`、`cursor/agent-b-*`、`cursor/agent-c-*` 检查相对 `main` 的改动文件。只允许改动对应目录，以及上表允许的 `pnpm-lock.yaml` 变化；否则 CI 失败。

## 6. PR 要求

每个子 Agent 的 PR 描述包含：

- **对应任务**：例如“B-M1-4 定制生成”。
- **覆盖的验收条目**：例如 P1～P11、M1～M9。
- **验证方式**：执行了哪些命令，结果如何。
- **已知限制和 `test.fixme`**（如果有）。
- **接口变更请求**（如果有）。
- **对其他 Agent 的影响**（如果有）。

## 7. 子 Agent 启动说明（主 Agent 派发任务时使用）

**通用部分（三个子 Agent 都包含）：**

> 你在 worktree `<路径>`、分支 `<分支名>` 上工作。开始前先完整阅读 `docs/01`～`docs/04`。产品的核心是“为每个客户生成一份独立的定制文案”，不是群发。你只能修改 `<目录>`；接口只能使用 `packages/shared`，需要修改接口时按 04 第 4 节提出请求。所有测试必须能在离线、没有任何 API Key 的环境中通过。不要把 Cursor 作为模型接口；不要在代码、测试或日志中写入任何密钥。按 04 第 2 节 M1 表格中你负责的那一列的顺序拆分 PR，每完成一项就提交、推送，并创建或更新草稿 PR。

**Agent A 补充：** 界面全部使用中文；审核界面要让运营快速看出“这份文案为这个客户定制了什么”（定制要点、原文与中文对照并排）；生成进度在刷新后仍然可以看到；每个页面至少有一个覆盖主要交互的组件测试；所有请求都通过 `src/api/` 中基于 `api.ts` 的客户端发出。

**Agent B 补充：** 合规逻辑（退订链接、同意过滤、删除）必须在服务端强制执行；客户简报的类型中不能包含姓名、邮箱、手机号、地址；备注在发给模型前必须遮盖隐私信息；每个客户最多调用 1 次模型；三个适配器都先实现离线版本；所有响应都用 shared schema 校验。

**Agent C 补充：** 测试文件按 03 的条目编号命名，例如 `C4-only-consented.spec.ts`、`P3-personalized-differs.spec.ts`；伪造的大模型服务要记录全部请求内容，用于检查个人信息隔离、备注是否被使用和调用次数；`acceptance/run.ts` 输出逐条结果，有失败时以非零退出码结束；M3 时录制演示视频。
