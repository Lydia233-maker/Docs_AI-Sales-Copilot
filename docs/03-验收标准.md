# 03 验收标准

> 版本：V1（第一版，可试用版）
> 状态：规划稿，等待负责人确认后开工
> 前置文档：[01 产品定位与需求](./01-产品定位与需求.md)、[02 技术方案与目录结构](./02-技术方案与目录结构.md)

第一版是否完成，以本文档中的条目为准。每一条都标注了验证方式：**E2E**（tests/e2e 中的 Playwright 测试）、**API**（tests/e2e/api 中的接口测试）、**单测**（apps 内的 Vitest 测试）、**人工**（演示或抽查）。Agent C 负责把标注为 E2E 和 API 的条目全部落实为自动化测试，并汇总到 `tests/e2e/acceptance/run.ts` 的报告中。

条目前缀：**G** 通用，**D** 数据，**N** 画像与备注，**A** 挑选客户，**H** 营销节点，**P** 定制生成（核心），**M** 模型与成本，**R** 审核，**E** 发送与导出，**T** 追踪，**C** 合规（重点），**K** 安全与配置，**Y** 试用就绪。

## 1. 通用标准（每个 PR 都必须满足）

- [ ] G1 在根目录执行 `pnpm install && pnpm build && pnpm test && pnpm lint` 全部通过。
- [ ] G2 所有测试在**离线且没有任何 API Key** 的环境中运行通过。
- [ ] G3 前后端交换的数据结构全部来自 `packages/shared`，apps 中没有重复定义接口类型（代码审查）。
- [ ] G4 子 Agent 的 PR 只修改自己负责的目录（CI 归属检查，规则见 04）。
- [ ] G5 后端对每个接口的响应都用 shared 中的 schema 校验，不一致时测试失败（API）。
- [ ] G6 卖家使用的界面全部是中文；外语只出现在文案内容和面向海外客户的退订页面（人工 + E2E 抽查）。

## 2. 数据导入（D）

- [ ] D1 上传 `fixtures/demo-pet` 中的客户和订单 CSV，预览显示的总行数、合法行数、错误行数与 `fixtures/demo-pet/README.md` 一致；**预览阶段不写入业务数据**（API）。
- [ ] D2 订单 CSV 中的多行商品被合并为一笔订单，样例中至少 3 笔多商品订单的金额和商品数正确（单测 + API）。
- [ ] D3 订单通过邮箱关联到客户；关联不上的订单在预览中单独计数（API）。
- [ ] D4 `fixtures/invalid/` 中的每个文件都会被拒绝，或者在预览中逐行列出行号、字段和原因（API）。
- [ ] D5 重复导入同一个文件时，新增数为 0，数据不重复（API）。
- [ ] D6 入库出错时整批回滚（单测）。
- [ ] D7 退款或取消的订单不计入消费（单测）。
- [ ] D8 处理 5 万行订单的 CSV 时，预览和入库各自在 60 秒内完成（人工，记录耗时）。
- [ ] D9 数据来源通过 `DataSource` 接口接入；`shopify-api` 适配器存在但只抛出“未实现”（代码审查）。

## 3. 画像与备注（N）

- [ ] N1 导入后，至少 5 位指定客户的订单数、累计消费、末购时间、消费层级、主要品类与 fixtures 中的期望值一致（单测）。
- [ ] N2 语言判定：带 `lang:es` 标签的客户、MX 国家且没有标签的客户、US 国家的客户，分别被判定为 es、es、en；销售手动修改语言后，以手动设置为准，重新导入也不会被覆盖（单测 + API）。
- [ ] N3 销售可以为客户添加和删除多条备注、修改偏好标签和客户类型，刷新页面后仍然保留（E2E）。
- [ ] N4 Shopify 客户 CSV 中的 `Note` 被导入为一条来源为“导入”的备注（API）。
- [ ] N5 保存包含邮箱或电话的备注时，界面显示隐私提醒；备注仍然可以保存（E2E）。
- [ ] N6 客户详情页展示画像、订单、备注和收到过的推广（E2E）。

## 4. 挑选客户（A）

- [ ] A1 导入演示数据后，4 个场景的人数和可触达人数与 fixtures 期望值一致（API）。
- [ ] A2 沉睡召回使用“≥ 60 天”的口径，第 59 天和第 60 天的边界正确（单测）。
- [ ] A3 没有导入弃单 CSV 时，弃购挽回显示“未导入弃单数据”，而不是 0 人（API + E2E）。
- [ ] A4 场景、条件（国家、语言、消费层级、品类、偏好标签、客户类型、是否有备注）和手动勾选可以组合使用，预览结果与直接查询数据库的结果一致（API）。
- [ ] A5 预览显示总人数、可触达人数、语言分布、逐个定制人数和小群方式人数（E2E）。
- [ ] A6 超过单批上限（默认 200）时，接口返回 `AUDIENCE_OVER_LIMIT`，界面提示需要缩小范围；修改 `OUTREACH_MAX_RECIPIENTS` 后上限随之变化（API）。

## 5. 营销节点（H）

- [ ] H1 首页展示未来 45 天内的营销节点，包括中文名称、日期、适用市场、建议预热日期和推荐场景（E2E，使用固定的测试日期）。
- [ ] H2 测试日期为 10 月 20 日时，列表中包含黑色星期五和亡灵节；测试日期为斋月开始前 30 天时，列表中包含斋月（API）。
- [ ] H3 从节点开始挑选客户时，推荐场景和节点信息已预先填好（E2E）。

## 6. 定制生成（P）——核心能力

- [ ] P1 **每个收件人一份草稿**：一次推广有 N 位可触达的收件人时，生成后正好有 N 份草稿；未同意营销的收件人不生成草稿，并显示排除原因（API）。
- [ ] P2 **生成方式判定**：订单数 ≥ 2、有备注或有偏好标签的客户使用逐个定制；其余客户使用小群方式；和 fixtures 期望值一致（单测 + API）。
- [ ] P3 **逐个定制确实不同**：使用伪造的大模型服务时，两位购买记录不同的客户收到的请求中，简报内容分别包含各自买过的商品；草稿内容互不相同（API）。
- [ ] P4 **备注被用于生成**：为客户添加备注“喜欢无尘猫砂”后生成，伪造大模型服务收到的该客户简报中包含这条备注（API）。
- [ ] P5 **按客户语言生成**：西班牙语客户的草稿是西班牙语，英语客户的草稿是英语；每份草稿都有中文对照（API）。
- [ ] P6 **小群方式**：同一小群的客户共用一次调用的结果，但渲染后的 `{{first_name}}` 和 `{{last_product}}` 是每个人自己的（API）。
- [ ] P7 每份草稿显示生成方式、使用的模型和中文定制要点（E2E）。
- [ ] P8 **后台生成与进度**：生成以后台任务执行，界面显示进度（总数、完成、失败）；生成过程中刷新页面，进度仍然可以看到（E2E）。
- [ ] P9 **部分失败不影响整体**：伪造大模型服务对其中 3 位客户的请求持续返回非法 JSON，且模板兜底也被关闭时，其余草稿正常生成，任务状态为 `partially_failed`；点击“重试失败的”后只重新请求这 3 位（API）。
- [ ] P10 单份草稿“重新生成”时，只替换这一份（API）。
- [ ] P11 **离线可用**：没有任何 Key 时，生成全部由模板完成，草稿标注“模板生成”，包含画像中的商品和品类，并且有中文对照（API + E2E）。
- [ ] P12 由人工抽查 1 次真实模型生成的推广（至少 20 份逐个定制的草稿）：≥ 80% 能看出是写给这个客户的；外语读起来地道；中文对照准确（人工，需要 Key）。

## 7. 模型与成本（M）

- [ ] M1 **每个客户只调用 1 次**：伪造大模型服务收到的生成请求数 = 逐个定制人数 + 小群数；同时生成邮件和 WhatsApp 时，请求数不变（API）。
- [ ] M2 **默认不做 AI 检查**：一次完整的生成过程中没有 `review` 用途的调用；点击“帮我检查”后才产生 1 次调用，并返回中文建议（API）。
- [ ] M3 **降级**：伪造的默认模型返回 500 错误时，改用链中的下一个模型，草稿标注“备用模型”，并排在审核列表前面（API）。
- [ ] M4 默认链中的模型都失败时，由模板兜底，生成不会中断（API）。
- [ ] M5 “用高质量模型重写”使用 `premium_rewrite` 链和 `OPENAI_PREMIUM_MODEL`；没有配置时按钮置灰并说明原因（API + E2E）。
- [ ] M6 把 `LLM_CHAIN_GENERATE` 设为 `doubao,...` 后，请求发往伪造的豆包地址（API）。
- [ ] M7 **生成前预估**：预估调用次数与 M1 的实际请求数一致；配置了单价时显示预估费用，没有配置时只显示调用次数和 token 数（API + E2E）。
- [ ] M8 每次调用都写入 `llm_calls`，包括用途、供应商、模型、是否降级、耗时、token 数和预估费用；**记录中不包含 Key**（API）。
- [ ] M9 并发数不超过 `LLM_CONCURRENCY`（伪造服务统计同时在处理的请求数）（API）。
- [ ] M10 代码中没有把 Cursor 作为模型接口的调用（代码审查 + 搜索检查）。
- [ ] M11 M0 阶段的模型对比报告已提交（`docs/model-benchmark.md`），包括 10 个演示客户在各候选模型上的质量评分、价格和速度，以及选定的默认模型（人工，需要 Key）。

## 8. 审核（R）

- [ ] R1 邮件正文缺少 `{{unsubscribe_url}}` 或 `{{company_address}}`、出现白名单以外的占位符、占位符未闭合、语言与客户语言不一致时，检查结果为“阻止”（单测）。
- [ ] R2 命中违禁词表或超长时为“警告”（单测）。
- [ ] R3 **审核列表排序**：阻止 → 备用模型或模板兜底 → 小群方式 → 警告 → 其余，与 02 第 4.7 节一致（API + E2E）。
- [ ] R4 有阻止性问题的草稿，“通过”按钮不可用，接口返回 409 `DRAFT_HAS_BLOCKING_ISSUES`（API + E2E）。
- [ ] R5 **一键通过**只通过“已生成且没有阻止性问题”的草稿，并返回通过数和跳过数（API + E2E）。
- [ ] R6 编辑草稿后重新执行检查，标记为“已修改”，刷新后保留（E2E）。
- [ ] R7 草稿详情页可以并排查看外语原文和中文对照，并显示填入个人信息后的预览（E2E）。

## 9. 发送与导出（E）

- [ ] E1 默认（没有设置 `EMAIL_SENDER`）为模拟发送：不访问网络；发送确认页和报表上明确标注“模拟发送”（API + E2E）。
- [ ] E2 **每封邮件内容不同**：逐个定制的收件人收到的是各自的草稿内容（API）。
- [ ] E3 只发送“已通过”的草稿；未通过的草稿不会被发送（API）。
- [ ] E4 渲染后不残留 `{{...}}`；`{{first_name}}` 为空时使用该语言的默认称呼（如 “there”、“hola”）（API）。
- [ ] E5 设置 `EMAIL_SENDER=smtp` 并指向伪造的 SMTP 服务后，邮件被投递到伪造服务，并带有 `List-Unsubscribe` 头（API）。
- [ ] E6 单封发送失败不影响其他邮件，失败原因被记录（单测）。
- [ ] E7 **复制**：点击“复制”后，剪贴板中是填入个人信息后的最终文本；可以标记为“已手动发送”，并计入报表（E2E）。
- [ ] E8 **WhatsApp**：可以复制文本；可以打开带文案的 wa.me 链接；批量导出的 CSV 包含手机号（E.164）、姓名、语言和文案；手机号无效的客户被排除（API + E2E）。
- [ ] E9 代码中没有任何 WhatsApp 自动发送的调用（代码审查）。

## 10. 追踪与转化（T）

- [ ] T1 模拟发送后，报表显示发送、送达、打开、点击、退订数，模拟数据带“模拟”标记；两次运行结果一致（API）。
- [ ] T2 点击追踪链接会记录事件并跳转；目标不是店铺域名时拒绝跳转（API）。
- [ ] T3 发送后导入 `orders_after_send.csv`，下单客户数和金额与期望值一致；归因窗口外的订单不计入（API）。
- [ ] T4 使用推广折扣码的订单被标注为“折扣码归因”（API）。
- [ ] T5 报表可以按“逐个定制”和“小群方式”分别显示转化率（API + E2E）。

## 11. 合规（C）——必须全部通过才能交付试用

- [ ] **C1 每封营销邮件都包含退订链接**：缺少 `{{unsubscribe_url}}` 的草稿不能通过审核；即使绕过前端直接调用发送接口，后端也会拒绝（`MISSING_UNSUBSCRIBE`）（API）。
- [ ] **C2 退订链接是收件人专属的**：每个收件人的退订 token 不同，且不可猜测（至少 128 位随机数）（API）。
- [ ] **C3 退订立即生效**：确认退订后写入 `unsubscribed_at`；之后创建的推广会以 `unsubscribed` 原因排除该客户；退订页面按客户语言显示英语或西班牙语，不需要登录（API + E2E）。
- [ ] **C4 只使用已同意接收营销的客户**：`email_consent=false` 的客户不会生成邮件草稿，也不会被系统发送；`sms_consent=false` 的客户不会出现在 WhatsApp 复制和导出中。演示数据中包含未同意营销的客户，断言他们在所有草稿、发送和导出结果中出现 0 次（API）。
- [ ] **C5 没有入口可以绕过同意过滤**：界面和接口都不提供“包含未同意营销的客户”的选项；对未同意营销的客户调用复制或渲染接口时返回错误（API + 代码审查）。
- [ ] **C6 发送前必须填写公司地址**：店铺没有填写公司地址时，真实发送返回 `MISSING_COMPANY_ADDRESS`（API）。
- [ ] **C7 可以删除单个客户**：删除后，在客户、备注、画像、订单、收件人、草稿、消息记录中都查不到该客户的邮箱、姓名、手机号和备注内容（直接查询数据库）；推广报表的汇总数字仍然可以显示（API）。
- [ ] **C8 可以清空店铺数据**：输入店铺名确认后，客户、备注、订单、弃单、推广、草稿和消息全部清空；店铺名输入错误时返回 `CONFIRMATION_MISMATCH`（API + E2E）。
- [ ] **C9 删除操作留有审计日志**：日志中只记录操作人、时间和数量，不包含被删除客户的个人信息（API）。
- [ ] **C10 发给模型的数据不含个人信息**：伪造大模型服务记录全部请求内容，断言其中不包含演示数据中任何客户的姓名、邮箱或手机号；备注中的邮箱和电话已被替换为 `[已隐藏]`（API）。

## 12. 安全与配置（K）

## 14. 端到端演示脚本（最终验收）

在没有网络和 Key 的干净环境中执行：

```bash
pnpm install
pnpm build
pnpm --filter api run create-user -- --email demo@example.com --store "Paws Demo"
pnpm --filter api run seed-demo -- --email demo@example.com
pnpm e2e              # Playwright 全部通过
pnpm acceptance       # 输出各条目的通过或失败报告；有失败时以非零退出码结束
```

然后人工演示（由 Agent C 录屏）：

1. 登录，首页看到即将到来的营销节点（如黑五）。
2. 打开一位老客户的资料，添加备注“养了两只布偶猫，喜欢无尘猫砂”，并添加偏好标签。
3. 从“黑五”节点开始挑选客户：消费层级为高、品类为猫用品，再手动勾选 2 位客户；预览显示逐个定制人数、小群方式人数和语言分布。
4. 填写推广意图“黑五老客专享 8 折，主推猫砂和猫粮，强调囤货划算”，渠道选择邮件和 WhatsApp；查看预估的调用次数。
5. 开始生成，看到进度条；完成后，每位客户都有自己的草稿：英语客户是英语，墨西哥客户是西班牙语，都有中文对照。
6. 审核列表顶部是需要重点看的草稿。删除其中一份的退订占位符，出现“阻止”提示，“通过”按钮不可用；恢复后通过。其余草稿一键通过。
7. 发送确认页显示被排除的“未同意营销”客户；执行模拟发送。
8. 复制一位客户的 WhatsApp 文案，并打开 wa.me 链接；导出 WhatsApp CSV。
9. 打开某位收件人的退订链接并退订；再创建一次推广，确认该客户被排除。
10. 导入 `orders_after_send.csv`，报表中出现下单客户数和金额，并按逐个定制和小群方式分开显示。
11. 删除一位客户，确认在客户列表和数据库中都查不到他。
12. （如果负责人提供了 Key）配置模型后重复第 5 步：标注了“布偶猫”备注的客户，文案中提到了无尘猫砂；对一份草稿点击“用高质量模型重写”。

## 15. 不在第一版验收范围内
